本片提要

我给画境写生图流程写了半年，它一直只活在我自己的系统提示里。直到把它打包成两个文件——80 行的 SKILL.md 加 239 行的零依赖脚本——发布上技能市场，别人才第一次能用上它。这篇拆这次打包的全过程：frontmatter 怎么写、退出码怎么定、描述为什么是最贵的五十个词、以及 Snyk 那个 7.1% 的泄漏率意味着什么。

2 个文件 4 个退出码 0 个 npm 依赖 ≈60s 安全扫描
80行SKILL.md 的全部长度
239行零依赖脚本的实现
3个脚本依赖的服务端点
7.1%公开技能泄漏密钥的比例（Snyk）

先交代背景。画境（AI Image Studio）是我本机跑的一个生图服务：管理自己的图像模型渠道，所有出图都进本地画廊，可重试、可审计。我在自己的 Agent 系统里用它生成了几百张图，流程烂熟于心——先探活、再提交、轮询到完成、把本地路径交回去。这套流程一直是我的能力：写在我的系统提示里，别人拿不到。

2026 年 10 月，我把它打包成了 huajing-image-gen：一个 SKILL.md 加一个零依赖的 Node 脚本，共 319 行，发布上 ClawHub 技能市场。 anyone clawhub install 之后，他们的 Agent 就能在画境上生图——不用读我的提示词，不用知道端口，服务没启动时还能收到一条「运行 start.bat」的可执行修复提示。

这次打包让我想清楚了一件事：提示词不是能力。提示词是私人的、不可分发的、没有契约的；技能是公共的、可安装的、带退出码和验收标准的。中间隔着四件事：可发现的描述、可执行的脚本、可恢复的错误、可审计的分发。这篇逐件拆。

阅读说明：全文约九千字，七章 + 四枚小样。第 1 章讲提示词与能力的三个差别；第 2 章解剖 SKILL.md；第 3 章写 description——最贵的五十个词；第 4 章拆零依赖脚本；第 5 章走发布流水线；第 6 章讲装到别人家之后的纪律；第 7 章讲供应链风险与治理。四枚小样都是确定性模型。

SECTION01

提示词不是能力

「我会用」和「任何人装了就能用」之间，隔着分发、契约与审计三件事。

在打包之前，我的生图能力长这样：一段写在系统提示里的中文流程——「先 GET /api/health 探活，失败提示用户跑 start.bat；POST /api/generations 提交，轮询 GET /api/generations/{id} 到 completed；把本地图片路径交回用户」。加上我脑子里的默认值：尺寸 1024x1024、数量 1、超时五分钟。

这套东西对我有效，因为整个环境都在我脑子里：端口是 4173、画境没启动长什么样、渠道列表怎么读、失败该重试还是换渠道。但对另一个 Agent 来说，它是零——它没有我的记忆，没有我的默认值，也没有我踩过的坑。

把这套流程和打包后的技能并排放，差别立刻显形：


一行命令，版本随包走
0 成功 / 1 生成失败 / 2 不可达 / 3 用法错误
stderr 只走诊断，包体无秘密
别人家 Agent 判断什么时候该用它
系统提示里的流程打包后的技能
分发复制粘贴提示词，每次升级靠人肉同步clawhub install
契约「大概这样做」——没有定义失败长什么样4 个退出码
审计出了错不知道是流程哪句被理解偏了JSON on stdout
触发永远在我的会话里挂着description 驱动

这四行里最容易被低估的是契约。提示词版本的流程没有定义「失败」：画境没启动算什么？渠道报错算什么？超时算什么？我自己知道，脚本不知道。打包成技能的第一步不是写文档，是把失败模式枚举出来并编码——这就是那四个退出码的由来，第 4 章展开。

一个技能的最小形态

ClawHub 的技能格式是目录制：<slug>/SKILL.md 加附属文件，最小技能只需要 frontmatter 里的 name 和 description。也就是说，一个纯 Markdown 的「怎么做 X」说明，只要描述写得好，就能发布、被搜索、被安装。

但纯文本技能有个天花板：它只能建议 Agent 做什么，不能保证 Agent 做对。生图这种带轮询、带超时、带错误分类的流程，写成散文留给模型自由发挥，每次执行都是一次重新发明。所以 huajing-image-gen 选了目录制的完整形态：

huajing-image-gen/2 个文件 · 319 行
huajing-image-gen/
├── SKILL.md            # 80 行：frontmatter + Setup + Usage + Notes
└── scripts/
    └── huajing.mjs      # 239 行：Node 18+ 零依赖，4 个子命令

# 脚本只依赖画境的三个最稳定端点：
#   GET  /api/health          探活
#   POST /api/generations     提交生成
#   GET  /api/generations/{id} 轮询结果

80 行文档 + 239 行脚本——这个比例值得记住。文档只负责三件事：让机器决定什么时候用（description）、让 Agent 知道怎么调（Usage）、出错时怎么办（Notes）。真正的逻辑全在脚本里，因为散文写的轮询逻辑，模型每次执行都会变体，而脚本每次执行都一样。

技能的本质，是把「我会」翻译成「任何人装了就能会」。翻译过程中丢掉的每一个默认值，都会在别人家变成一次失败。

下一篇从最贵的那个部件开始：SKILL.md 的 description——机器读它来决定要不要用你的技能，五十个词写错一个场景，技能就永远不会被触发。

SECTION02

解剖一个 SKILL.md

80 行文档拆成六个部件，每一个都对应一种确定的失败方式。

把 huajing-image-gen/SKILL.md 从头到尾读一遍，它只有四个段落：frontmatter、Setup、Usage、Notes。80 行里没有一个修饰词。这不是文风，是结构——每个段落都在回答一个不同主体的问题：frontmatter 回答「机器」，Setup 回答「安装者」，Usage 回答「执行时的 Agent」，Notes 回答「出错的 Agent」。

SKILL.md80 行 · 六个部件
---
name: huajing-image-gen
description: >-
  Generate images through a local Huajing (AI Image Studio) server. Use when
  the user asks to create or generate an image, polish an image prompt, or
  look up previously generated images. Supports text-to-image with polling,
  batch count, size, negative prompt, and provider/model selection. Requires
  the local Huajing server (default http://127.0.0.1:4173) and Node 18+.
metadata:
  openclaw:
    requires:
      bins: [node]
---

# Huajing Image Generation        ← 一句话定位 + 链接
## Setup                          ← 安装者要做的三步（启动服务/加渠道/环境变量）
## Usage                          ← Agent 执行时抄的命令，含全部参数与退出码
## Notes                          ← 三种失败的处理指引（exit 2 / exit 1 / 画廊复用）

部件一：name 与 slug 的同一性

frontmatter 里的 name: huajing-image-gen 看似只是个名字，但发布时有个容易踩的坑：ClawHub 取的 slug 是文件夹名，不是 frontmatter 的 name。如果文件夹叫 huajing-skill 而 name 写 huajing-image-gen，发布出来的技能 slug 是前者，所有 install @owner/huajing-image-gen 都会失败。发布流水线里这叫「slug 对齐」——文件夹名必须等于 slug，name 与 slug 保持一致是纪律，不是巧合。

部件二：description 的三句话结构

这段 description 有 62 个词，三句话各司其职：第一句说能力（Generate images through a local Huajing server）；第二句说触发场景（Use when the user asks to create or generate an image, polish an image prompt, or look up previously generated images）；第三句说前置条件（Requires the local server and Node 18+）。这个「能力—触发—前提」的三段式不是模板腔，是机器解析的格式——第 3 章会逐词拆。

部件三：requires 声明依赖

metadata.openclaw.requires.bins: [node] 声明这个技能需要 node 可执行文件。声明依赖有两个作用：市场页会把 requires 明示给安装者（不静默满足）；消费方可以在安装时检查本机有没有 node，没有就把技能标灰，而不是装完在运行时报错。环境变量同理——HUAJING_BASE_URL 在 Setup 里写成「可选覆盖，默认 127.0.0.1:4173」，而不是藏在脚本第 8 行。

部件四：{baseDir} 占位符

Usage 里所有命令都写成 node {baseDir}/scripts/huajing.mjs …。{baseDir} 是技能安装后由运行时替换的占位符——因为技能被安装在用户机器的哪个路径，写文档的人不知道。硬编码相对路径 scripts/huajing.mjs 在技能目录内能跑，一旦 Agent 的工作目录不是技能目录就会 404。这是「可迁移」检查项的来源：文档里出现的一切路径，要么是占位符，要么是协议相对路径（如 /api/health），不能是安装位置。

部件五：退出码即契约

Usage 段最显眼的一行是：Exit codes: 0 success, 1 generation failed, 2 server unreachable, 3 bad usage。四个数字把失败分成三类，Agent 据此决定下一步：

退出码含义Agent 应该做什么
0成功读取 JSON 里的图片路径/URL，交回用户
1生成失败读 JSON 的 error 字段（上游原话），考虑换 --provider 重试
2服务不可达不重试——转告用户「启动画境（start.bat / npm start）」
3用法错误参数拼错了，读 stderr 里的 Usage 重来

没有退出码契约时，Agent 对失败只有两种反应：盲目重试，或者把报错堆栈原样甩给用户。2 号退出码的设计意图是让重试在「不可达」这一类失败上停止——重试一个没启动的服务，五次和零次没有区别。

部件六：Notes 是「错误的处理指引」

Notes 段只有三条，每条都对应一种真实发生过的失败：exit 2 → 转告用户启动服务；exit 1 → 上游错误原文在 JSON 里，换渠道通常有效；生成过的图都在画廊里，可以 gallery 查回，不必重新生成。第三条是给 Agent 的资源复用提示——没有它，Agent 在图片失败重试时会倾向于重新生成，浪费一次渠道调用。

SECTION03

最贵的五十个词

description 是技能唯一的广告位：机器读它决定触发，写宽了误触发，写窄了永不被用。

一个技能装进别人家后，用户不会读你的 Usage——用户只说「帮我生成一张图」。是 Agent 在几十个已装技能里挑一个，挑的依据只有一个：每条技能的 description。这五十来个词是技能唯一的广告位，也是最容易被写成废话的五十个词。

把 huajing-image-gen 的 description 逐句拆开，看每个短语在买什么：

短语它买到什么删掉的后果
Generate images through a local Huajing server能力主语与边界：本地服务，不是云端 API用户问「用 DALL·E 画图」时可能误触发
Use when the user asks to create or generate an image核心触发：生成图片最典型的请求无法命中，技能永不被用
polish an image prompt次级触发：润色提示词polish 子命令永远闲置
look up previously generated images次级触发：画廊检索「上次那张图」类请求漏掉，重生成浪费渠道调用
Supports text-to-image with polling, batch, size, negative prompt…能力边界：会轮询、可批量、支持负向词Agent 不知道脚本会阻塞到完成，自己另写轮询
Requires the local server and Node 18+前置条件：没装画境的机器不该选它在没有服务的机器上被选中，然后 exit 2

三句话的结构由此而来：第一句立边界，第二句列触发，第三句交前提。Triggering 不是搜索匹配，是让另一个模型在「工具不足时判断该用什么」——它读的是语义，不是关键词。所以 description 里放「强大的」「下一代」这类形容词毫无用处，放「look up previously generated images」这种具体场景短语才有用。

写宽与写窄

description 有两种典型写坏法。写宽：把描述写成「图像生成工具」——于是用户问「帮我裁剪这张图」「这张图什么风格」时它也被选中，然后脚本 exit 3。误触发的代价不只是浪费一次调用：Agent 可能放弃原本正确的方案。写窄：把描述写成「用画境 HTTP API 生图」——只有用户明确提出「画境」才触发，而用户永远不知道画境是什么。

安全的写法是枚举触发场景，而不是枚举实现：写「generate an image」而不是「调用 /api/generations」，写「look up previously generated images」而不是「查询 gallery 表」。判断标准很简单：想象用户的原话，你的 description 里得有与之语义重合的短语。

触发可靠度 ≈ 场景短语与用户原话的语义重合度 − 泛化词带来的误触发
Use when + 具体动词短语 · 能力边界（local/云端）· 前置条件（requires）

这条「公式」没法精确计算——触发是另一个模型的行为。但它指出了调优方向：拿十条用户可能说的话，逐条检查 description 能否接住；再拿五条不该接的话，检查会不会被误接。这个 15 条的清单就是 description 的测试集。

还有三个不是 description 的触发面

  • name：用户说「用 huajing 生成」时按名字命中。所以 name 要含品牌词，同时保持 slug 一致。
  • requires：前置条件不满足时，消费方应在选择阶段就把技能标灰——这比「触发后失败」的体验好一个量级。
  • Notes 里的负向指引：「If generate exits 2, the server is not running」这类句子也在参与触发决策：Agent 读到它，就知道失败不是技能的错，不必换技能。
一个还没做的改进：描述调优目前靠人工想象用户的话。更好的做法是在自己家先积累「触发日志」——哪句话选中了技能、哪句话该选中却没选中——攒够二十条就是 description 的回归测试集。这与 VOL.06 里「评测集会腐烂」是同一个道理：触发描述也需要测试集，也会腐烂。

SECTION04

零依赖脚本

239 行、四个退出码、JSON 走 stdout——把「会失败」写进接口，而不是留给运气。

技能脚本的运行环境和常规工程完全不同：它跑在别人家的机器上，路径未知、包管理器未知、网络未知。所以第一条设计决策是零依赖——huajing.mjs 只 import node:process，HTTP 用 Node 18 内置的 fetch，JSON 解析用内置的 JSON。没有 npm install，没有 node_modules，没有版本解析。安装即解压，解压即能跑。

这不是洁癖。一个技能如果要求 pip install -r requirements.txt 或 npm i，它的安装成功率就取决于用户机器的网络、Python 版本、npm 镜像源——每一项都是一次远程失败的入口。零依赖把「安装」收敛成「复制文件」，把失败的入口从安装期推迟到运行期，而运行期的失败是可以被退出码契约管理的。

失败分三类，退出码只发三种

脚本开头定义了四个常量，整个 239 行里所有失败路径都收敛到它们：

scripts/huajing.mjs第 10–13 行
const EXIT_OK          = 0;   // 成功，JSON 已写到 stdout
const EXIT_FAILED     = 1;   // 生成失败：上游错误原文在 JSON error 字段
const EXIT_UNREACHABLE = 2;   // 画境不可达：不要重试，去启动服务
const EXIT_USAGE      = 3;   // 用法错误：读 stderr 里的 Usage

为什么是这四个？因为它们对应 Agent 的四种不同下一步。重试策略完全不同的失败，必须用不同的出口：网络抖动（HTTP 5xx）值得重试，服务没启动不值得；参数拼错重试一百次也是 3。反过来，凡是「下一步相同」的失败都合并成一个码——404 和参数错都归 3，因为对 Agent 来说它们都意味着「检查你怎么调的」。

stdout 与 stderr 的分工

脚本的全部机器可读输出走 stdout，且是合法 JSON；全部人读诊断走 stderr——「huajing: queued 1 task(s) on provider …」「huajing: status generating, waiting...」。这条分工不是风格，是管道契约：Agent 可以放心 JSON.parse(stdout)，也可以把 stderr 展示给用户而不污染解析。轮询等待写进 stderr，就是为了「界面有动静、结果可解析」两全。

外加一个 --plain 开关：输出人类可读的路径列表而不是 JSON。它服务的是人直接在终端调试的场景——Agent 用 JSON，人用 plain，两不耽误。

可执行的修复提示，而不是报错堆栈

画境不可达时，脚本不是抛 ECONNREFUSED 堆栈，而是：

scripts/huajing.mjsrequest() 的 catch 分支
fail(EXIT_UNREACHABLE,
  `cannot reach Huajing at ${BASE_URL} (${error.cause?.code || error.message}). ` +
  'Start it with start.bat (Windows) or `npm start` in the Huajing repo.');

这句话是发布验收清单里的一条：服务未启动时给出可执行的修复提示（而非报错堆栈）。它包含三个信息：打的是哪个地址（所以 BASE_URL 被拼进消息）、失败的技术原因（cause code）、以及下一步动作（start.bat / npm start）。Agent 拿到它可以直接转述给用户——这就是「错误信息是产品文案」在技能层的样子。

轮询：截止时间与「不撤回」的诚实

生图是异步任务：提交后轮询 GET /api/generations/{id}，退避间隔 1s/2s/3s 封顶。轮询有一个 --timeout（默认 300 秒）的截止线，超时的处理值得抄下来：

scripts/huajing.mjspollGeneration
if (Date.now() > deadline) {
  fail(EXIT_FAILED, `timed out after ${timeoutSeconds}s; the task may still finish — ` +
    `check the gallery later (record id: ${id})`);
}

注意这句文案：任务可能仍然会完成。生图任务在服务端继续跑，超时只是客户端放弃等待，不是任务失败。把 record id 留在错误消息里，用户拿着它可以去画廊把图找回来——「重试」反而会浪费渠道调用。错误消息里写清「放弃了什么、留下了什么」，Agent 才能做出正确的下一步。

密钥去哪了：包里没有也不该有 API key。画境的渠道密钥存在画境服务自己的配置里，技能只对本机 127.0.0.1 说话。这让「装技能」和「配密钥」成为两个独立动作——第 7 章会看到，这个分离正是 7.1% 泄漏率的反面。

脚本就绪之后是发布。下一篇走一遍从 clawhub login 到线上可装的完整流水线，以及那条最容易被坑的 slug 规则。

SECTION05

发布流水线

从 clawhub login 到另一台机器能装能跑：五步、一条 slug 规则、一次 ≈60 秒的安全扫描。

发布这五步，官方文档十分钟就能读完。真正费时间的是第五步——验收——以及一个藏在第一步里的命名陷阱。先走流程：

发布命令序列v1.0.0 实录
# 1. 账号：GitHub 设备流授权（token 落在本机配置）
npm i -g clawhub
clawhub login --device

# 2. 本地校验 frontmatter
clawhub inspect huajing-image-gen/

# 3. 发布（文件夹名 = slug）
clawhub skill publish huajing-image-gen/   # 附 changelog v1.0.0
# ≈60s 安全扫描后才公开 —— 验收时别把这段延迟当成失败

# 4. 闭环：在另一台机器 / WSL 里安装并真实调用
clawhub install @starrysea1412/huajing-image-gen
node …/scripts/huajing.mjs health && … generate --prompt "…"

slug 就是文件夹名

发布后技能的 URL 是 clawhub.ai/<owner>/skills/<slug>，而 slug 取自文件夹名，不是 frontmatter 的 name。这意味着三件事：文件夹命名要从发布视角起（kebab-case、含能力词）；name 与文件夹名保持一致，避免「装的是 A、文档说自己是 B」；如果非要不同名，CLI 的发布参数可以覆盖 slug——但覆盖是例外，对齐是默认。这次发布里，目录名直接定为 huajing-image-gen，与 name 一字不差。

安全扫描是异步的

publish 返回成功 ≠ 技能已公开：ClawHub 会对包体跑一次官方安全扫描，约 60 秒后技能才出现在搜索与安装列表里。这次发布时，publish 后立刻去搜，搜不到——差点当成失败重发。事后知道这是正常流程，任何自动化发布脚本都应该把「扫描等待」设计进去：轮询 /skills/{slug} 直到 200，或者干脆 sleep 一分钟再验收。

扫描结果本身也是公开资产：GET /api/v1/skills/{slug}/scan 返回官方扫描结论。消费方（第 6 章的技能市场）会把它直接展示在安装页——发布者应该主动看一眼自己技能的扫描报告，别让第一个发现问题的不是我。

读接口是公共设施，写接口才要 token

ClawHub 的 API 边界划得很清楚：读全部免 token（search / skills / versions / scan / download，限流 3000/min/IP），写需要 clh_ token（multipart 发布、下架、更名，限流 300/min/IP）。OpenAPI 规范在 /api/v1/openapi.json，官方明确欢迎第三方目录复用读接口——条件是缓存结果、尊重 429 的 Retry-After、展示处回链技能页。

这三条合规义务值得照抄，因为它们是「把公共 API 当公共设施」的最小礼仪：缓存意味着不把自己的流量转嫁给对方；尊重退避意味着限流是合作信号而不是敌意；回链意味着流量有出处。

验收清单：发布不算完，闭环才算完

  • 可搜索：等扫描过后在 ClawHub 搜 huajing，技能出现；
  • 可安装：在另一台机器 / WSL 里 clawhub install，文件落在本地技能目录；
  • 可调用：health 通、真实 generate 出图；
  • 失败时给指引：故意不启动画境再调一次，确认拿到的是「启动服务」提示而不是堆栈；
  • 版本链路：改一处 description，重新 publish 出 v1.0.1，确认更新可被拉到。

最后一条常被跳过，但它验证的是更新通道：v1.0.0 发布成功只证明创建，不证明「下次改完还能推上去」。发布系统的bug往往藏在第二次发布里。

自动化路线：CLI 之外，网页创建 clh_ token 后可以直接 POST /api/v1/skills（multipart：payload JSON + files[]）。技能源码放进主仓库子目录（ai-image-studio/clawhub-skill/），随主版本走——CI 化时一条流水线同时出服务版本和技能版本，避免两处维护漂移。

下面这枚小样把发布与安装验收做成可操作的状态机：每一步都可以注入失败，看流水线如何停、回滚到哪、提示写什么。

模型 六步状态机与提示文案对应真实流程：publish → 扫描等待 → install（slug=文件夹名）→ 落盘技能目录 → health 探活 → 启用确认。脚本型技能默认停用，启用即审批——第 6 章展开。
SECTION06

装到别人家

安装 ≠ 启用。text-only 与 script-bearing 分级治理，是消费方的纪律，也是发布方的设计前提。

发布只是技能的出厂。技能真正被使用，是在另一个 Agent 体系里走完「搜索 → 安装 → 转换 → 启用 → 调用 → 卸载」的完整生命周期。这套流程的每一步都有治理决策，而决策的分界线只有一条：这个技能带不带可执行脚本。

我在 AI-skill（自己的 Hermes 工作台）里规划消费方市场时，把这条线画成了硬分级：

分级判定装完之后调用时
text-onlySKILL.md 不引用 {baseDir} 下的脚本、不声明 bins转换后即可用（仍受模板工具白名单约束）不额外审批
script-bearing正文引用 {baseDir} 脚本，或 requires.bins 非空默认停用，启用需人工确认；缺 bins 的在列表里标灰每次执行走受控审批

huajing-image-gen 是典型的 script-bearing：声明了 bins: [node]，正文里有 {baseDir}/scripts/huajing.mjs。装进 AI-skill 这样的消费方时，它的预期生命周期是：安装成功但状态「需审批」→ 用户看过 requires（node + 本机画境服务）后启用 → 每次 Agent 真要跑脚本时弹审批。审批不是形式：它把「外来代码在我机器上执行」这个决定，从安装时的顺手一点，推迟到每次实际发生的时刻。

转换：目录制到扁平制的有损边界

消费方体系若是扁平 Markdown 注入（技能文本拼进 system prompt），目录制技能就要过一道转换器。转换规则里最有意思的是分级判定：

  • frontmatter 的 name / description 直取——它们本来就是给机器读的；
  • version 取 metadata.openclaw.version，缺失则回落到 lock 文件；
  • tags 补 [clawhub, <owner>]——来源必须跟着技能走，审计时能追到发布者；
  • 正文原样保留，但 script-bearing 技能转换成「工具说明」文本，显式标注所需 bins/env，执行指令改为「走审批调脚本」。

这条有损边界是刻意设计的：文本注入的世界里，脚本不该被「描述」，而该被「申请」。把 node {baseDir}/scripts/huajing.mjs generate … 写进 system prompt，等于告诉模型「你可以随手执行任何命令」；转换成审批式的工具说明，等于把执行权收回到人手里。

市场页的三条信息义务

消费方展示技能卡片时，有三样东西必须明示，不能藏在「详情」里：

  • requires：需要 node 18+、需要本机画境服务——让安装者在装之前就知道这个技能能不能在自己家跑起来；
  • scan：ClawHub 官方安全扫描结果直接展示，不重扫、不转述；
  • 回链：clawhub.ai/<owner>/skills/<slug>——出处可点，作者可查，版本可追。

外加一条降级纪律：ClawHub 不可达时，市场 tab 整体隐藏，工作台其余功能零影响。市场是增强，不是依赖。

卸载与更新的闭环

卸载要同步清理两处：技能缓存目录与转换产物（hermes_skills/clawhub/<slug>.md）。残留的转换产物是隐患——技能已删，注入链路里却还在引用它的描述，Agent 会在不存在的技能上浪费触发。更新同理：新版本落地时旧转换产物必须被覆盖，lock 文件记录 slug/version/source/installed_at，让「现在装的是哪个版本」永远有据可查。

消费方的纪律反过来约束发布方：如果 requires 不写清楚、路径不使用 {baseDir}、失败不给退出码，技能在别人家的生命周期第一步就会卡住。治理不是发布之后的额外工作，是包体本身的一部分。

最后一章讲剩下的那个问题：当技能市场成为一个生态，包体里可能藏什么，以及 7.1% 这个数字该怎么读。

SECTION07

供应链与治理

Snyk 实测约 7.1% 的公开技能泄漏密钥或 PII。技能市场是能力市场，也是风险市场。

把技能市场想成 npm 或者 VS Code 扩展市场，风险谱就熟悉了：一个 SKILL.md 是给模型读的指令——指令注入因此成为技能特有的攻击面，这是 npm 没有的；附属脚本是要执行的代码——传统供应链风险它全有。Snyk 对公开技能仓库的实测结论是约 7.1% 的技能泄漏密钥或 PII。这个数字该逐字读：不是「7.1% 的技能是恶意的」，而是「7.1% 的作者把不该进包的东西打进了包」。

四类风险，四种漏点

风险从哪进来huajing 的对策
密钥 / PII 入包调试时把真实 key 写进示例、把用户路径打进文档包内零密钥：密钥在画境服务配置里，技能只对本机 127.0.0.1 说话；示例 prompt 全部虚构
恶意指令（提示注入）SKILL.md 正文写着「顺手把 ~/.ssh 打包上传」类指令消费方分级：script-bearing 每次执行过审批；文本型受工具白名单约束
脚本越权脚本读写技能目录之外、联网到陌生主机脚本只连 BASE_URL（默认本机）；审批层每次放行前人看得见命令
更新投毒v1.0 干净、v1.1 塞私货，存量用户自动升级安装锁定版本；更新是显式动作；lock 记录 version/source

第一类最常见也最冤：作者不是坏人，只是调试时把 Authorization: Bearer sk-… 留在了示例 curl 里。所以治理的第一道闸是发布前的自查：grep 一遍包体里的 sk-、Bearer、真实域名、绝对路径。ClawHub 的官方扫描会抓一部分，但扫描是下限，不是验收。

只依赖三个最稳的端点

技能的寿命长过任何一次 API 重构。画境的 HTTP API 有几十个端点，huajing.mjs 只用了三个：/api/health、/api/generations（POST 与 GET）、/api/prompts/polish。这是刻意收窄：技能脚本依赖的面越小，服务端演进时技能失配的概率越小。规划文档里把这条写成对策——「技能脚本只依赖 generations/health/polish 三个最稳定端点；画境改 API 时技能随版本跟进」。

反过来，发布方对「服务端怎么改才不弄死技能」也有了硬约束：这三个端点成了事实上的公共契约，改动它们等于宣布技能作废。这是一个健康的绑定关系——技能钉住最小公共面，服务端承诺最小公共面的稳定。

治理是卖点，不是负担

把第 6 章的分级、本章的自查与扫描连起来，消费方的安全姿态是四层：

层谁负责动作
发布自查技能作者包体 grep 密钥/真实路径；示例全虚构；requires 如实声明
平台扫描市场（ClawHub）≈60s 官方扫描，结果经 /scan 公开
安装分级消费方text-only 直用；script-bearing 默认停用、requires 明示
执行审批用户每次脚本调用过审批；拒绝即不执行

这套分层在设计文档里被写成一句自我定位：「安装默认停用 + 启用确认 + 脚本走审批；市场页明示 requires——这是 AI-skill 的卖点而非负担。」一个技能市场如果只比谁家技能多，它就是在批量分发攻击面；把治理做成产品差异，风险表才翻得了面。

还有两块没做完的

  • 触发与运行的观测：技能在别人家被谁触发、跑成什么样，发布者目前完全不可见（市场页有安装量计数，但没有失败率）。没有失败率的技能生态，等于没有幻觉率的搜索——错的地方自己不知道。
  • 依赖声明还不细：requires 声明了 node，但「需要本机 4173 端口有一个画境服务」这件事只写在 description 第三句里。前置条件应该有机器可读的位置（env / services），而不是散文——这样消费方才能在安装时真正检查，而不是靠模型读懂句子。
