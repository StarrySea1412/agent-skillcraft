结语：能力要能离开你

打包不是把提示词存成文件，是把「我会」翻译成「任何人装了就能会」。

把这次打包收拢，它其实只做了三件事：立契约（四个退出码、JSON 走 stdout）、留路标（description 的三段式、requires 明示、{baseDir} 占位）、交底（Notes 里的失败指引、scan 公开、回链可查）。三件事都不难，难的是心态——把「我自己知道就行」换成「拿到包的人一无所知」。

319 行、2 个文件，换来的是能力第一次离开了我：它可以在任何装了 Node 的机器上被另一个 Agent 调用，失败时有路标，出处可追，版本可锁。这就是「技能」和「提示词」的全部区别，也是全部价值。

三条可以搬走的做法

RULE 01 / 先枚举失败，再写流程

退出码是技能的骨架：把失败按「下一步该做什么」分类（重试 / 转告 / 检查用法），每一类一个出口。错误消息里写清「打的是哪个地址、失败的技术原因、下一步动作」——这是给 Agent 的，不是给人的。

RULE 02 / description 是给机器读的测试集

用「能力—触发—前提」三段式：第一句立边界，第二句列具体触发场景，第三句交前置条件。拿十条用户原话检查能不能接住，再拿五条不该接的话检查会不会误接。

RULE 03 / 依赖面越小，寿命越长

技能脚本只钉住服务端最稳定的最小端点集；requires 如实声明；密钥永远不进包。发布前 grep 一遍密钥与真实路径，平台扫描是下限不是验收。

这篇文没解决的问题

触发没有测试集。description 的调优靠人工想象用户原话；触发日志（哪句选中、哪句漏选）还没有落盘，攒够二十条才能做成回归集。

前置条件还是散文。「需要本机 4173 端口有画境服务」写在 description 里，requires 位置还没有机器可读的服务依赖声明，消费方无法在安装时真正检查。

发布者看不到运行情况。安装量有计数，失败率没有。技能在别人家跑挂了，我是最后一个知道的。

消费方市场还没落地。分级治理（默认停用 / 审批 / scan 展示）目前是规划与骨架，AI-skill 的技能市场尚未上线——这篇文里的「第 6 章」有一半还是设计，不是实现。

更新投毒只能靠锁版本。作者账号被盗后推送恶意更新，现有的 lock 与审批能拦住执行，但拦不住「已自动拉取」。内容寻址（按哈希安装）是更彻底的解，还没有做。
